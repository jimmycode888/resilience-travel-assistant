## 一、总体结论

**一句话：视觉与信息层级相比上一版是脱胎换骨的进步，但内容层跑到了契约之外——它做的其实是「另一条走廊、另一套路线」的产品，而不是本项目当前冻结的那一个。**

- **进步（值得肯定）**：上一版评审点名的 4 条 P0 基本全部落地——数据可信度（FIXTURE 标注 + 资料透明度）、状态覆盖（加载/不确定/不可用/错误四态）、把切换条件独立成块、到达时间改为区间并给信心加「演示估算」限定。这几点做得很到位。
- **致命问题（必须先解决）**：整条**走廊、地点枚举、三条候选路线、可用交通方式**全部与 `src/lib/corridor/index.ts`、`API_CONTRACT.md` 和三个黄金 fixture 不一致。设计稿的地点（西营盘/九龙湾/观塘/启德/湾仔）在契约里**根本不存在**。这意味着 D 无法用现有 `/api/decision` 复现任何一屏，三个情景的数据也全部对不上。
- **次要但会被评委当场问倒**：三处界面自相矛盾（「服务正常」却发生港铁故障；「港岛线→观塘线」一次转乘不成立；时间基准 07:51/07:56/08:00 打架）。

**粗略打分**（沿用上一版口径）：视觉与信息层级 **9/10**；契约字段对齐 **6/10**；界面数据自洽 **4/10**；范围合规 **3/10**。

**结论**：
- 若团队坚持既定走廊（坑口 ↔ 中环）→ 设计稿**改内容、保版式**即可，版式可以冻结为 v2。
- 若团队其实想换走廊（西营盘 ↔ 九龙湾）→ 这**不是 UI 修改**，而是一次**契约变更**：必须由 A 更新 `types/`、`corridor/`、三个 fixture，重跑 golden / smoke，并同步 B / C / D，否则演示必然穿帮。

## 三、必须改（P0）

### P0-1（最严重）走廊、地点、路线与已锁定契约完全不符

设计的起终点、候选路线与交通方式，全部**不在**契约枚举里：

| 维度 | 已锁定契约 / 实作（唯一真相） | 新版 Figma 设计稿 | 判断 |
|---|---|---|---|
| 走廊 | 将军澳（坑口）↔ 中环，`id: tko-hang-hau-to-central` | 西营盘/中环/湾仔 → 九龙湾/观塘/启德 | ❌ 另一条走廊 |
| 起点枚举 | 2 个：坑口（富宁花园）、坑口站 A 出口 | 3 个：西营盘·皇后大道西、中环·国际金融中心、湾仔·会展站 | ❌ 无一匹配 |
| 终点枚举 | 2 个：中环（交易广场）、中环（国际金融中心二期） | 3 个：九龙湾·宏照道、观塘·创纪之城、启德·AIRSIDE | ❌ 仅「中环 IFC」概念接近，且库里它是**终点**、设计里是**起点** |
| 候选路线 | R1 港铁主线（将军澳线→港岛线）、R2 过海巴士（东隧）、R3 港铁经鲗鱼涌 | 港铁优先（港岛线→观塘线）、的士直达、巴士 101、过海的士、巴士 101 + 港铁 | ❌ 全部不同 |
| 交通方式 | `TransportMode = mtr \| bus \| minibus \| walk \| tram \| ferry`（**无 taxi**） | 出现「的士直达」「过海的士」 | ❌ 契约外新增方式 |
| 巴士编号 | README 明确「未使用真实路线编号；正式版需由 B 核对官方资料后填入」 | 直接写「巴士 101」 | ⚠️ 需 B 核实 |

**后果**：
1. D 无法用现有 `/api/decision` 复现任何一屏；把设计落到代码会立刻触发 `400 INVALID_INPUT`（未知地点）。
2. 三个黄金 fixture（normal / heavy_rain / disruption）的建议出发时间、主路线、信心、切换条件**全部对不上**，`npm run smoke` 与设计演示会互相打脸。
3. 「切换情景会得到不同建议」这个演示脚本核心，在真实数据下不成立。

**改法（二选一，必须由 A 拍板）**：
- **方案 A（推荐，成本低）**：设计稿**改内容、保版式**——地点换成 坑口（富宁花园）/坑口站 A 出口 → 中环（交易广场）/中环 IFC；路线文案换成 R1/R2/R3 的 `label`；Plan B 用 R2 过海巴士，不要用「的士」。
- **方案 B（成本高）**：走契约变更流程。先改 `API_CONTRACT.md` + `types/` + `corridor/index.ts`，再由 B 换数据、C 重算、D 重跑 golden/smoke 与全部 15 个测试文件，并全组同意。**没有走完这个流程前，设计稿不能进实现。**

### P0-2 输入页的起终点组合超出「单一走廊」范围

- 契约：`origin` / `destination` 是**严格枚举**，各 2 个值；未知值会被 strict schema 拒绝（`API_CONTRACT.md §1.3`）。
- 设计：起 3 × 终 3 = **9 种组合**，其中仅极少数能在后端解析；且呈现为自由可换（两栏还带一个交换按钮），暗示支援任意两地对调。
- 上一版评审 P1-5 已经明确要求「收敛为走廊预设单选，并注明只支援一条走廊」，本次设计反而扩大了范围。
- **改法**：收成契约里的 2 × 2；页面文案点明「首版只支援一条固定通勤走廊」；去掉交换按钮。

### P0-3 结果页缺「最迟出发时间」（`latestDepartAt`）

- 契约的 `latestDepartAt`（不计额外缓冲的最迟起程时间）是「几点前必须走」的关键，也是本项目区别于地图的核心输出之一。
- 设计只有「建议 08:05 出发」与「为确保 09:00 前到达」，**没有「最迟 08:xx 前离开」**。上一版评审的 P0-4 就已提出，仍未补齐。
- **改法**：在一句话决策卡里把「建议出发」与「最迟出发」并列，例如 `建议 08:05 出发 · 最迟 08:15 前离开起点`。

### P0-4 三处界面自相矛盾（路演会被当场问倒）

**a) 顶部状态与情景冲突。** 页头固定显示「● 服务正常」，但「交通中断」情景正文写「金钟站信号设备故障，列车班次约每 8–10 分钟一班」；「不可用」「错误」状态下页头**仍然**写「服务正常」。
→ 改法：页头状态应由 `primaryPlan.status`（ok / delayed / disrupted / unknown，见 `labels.ts: STATUS_LABELS`）驱动，不要写死。

**b) 「港岛线 → 观塘线」单次转乘不成立。** 时间轴写：`08:12 港铁 港岛线 → 08:24 转乘 观塘线 → 08:42 到达`，即只用一次转乘。但港岛线与观塘线**没有任何交会站**（港岛线在中环/金钟/北角一带，观塘线在油麻地/太子/九龙湾一带），现实中至少需要 2 次转乘（经荃湾线，或经将军澳线到油塘）。这条路线在事实层面站不住脚。
→ 改法：换成契约里真实存在的转乘结构（将军澳线→北角→港岛线，或经鲗鱼涌），或补齐中间线路与转乘点。

**c) 时间基准打架。** 页头「演示固定资料 · 08:00 HKT」，但中断情景写「信息来源：港铁服务更新 · **07:51**」「建议 **现在 · 07:56** 出发」。若快照时间是 08:00，则 07:56 的「现在」是过去时间。
→ 改法：所有时间锚定到 `dataUpdatedAt`（`API_CONTRACT.md §1` 规定决策层永不使用「现在时间」来计算），并且「现在」只能来自注入的固定 now，不能与快照时间冲突。

### P0-5 「不确定」状态与契约语义不符

- 契约（`API_CONTRACT.md §2.4`）：`status = uncertain` = **有可行路线**，但到达信心为 `low`，**或**没有可用 Plan B——使用者「可以出发，但要预留更多时间」。也就是说 `uncertain` **仍要输出** `departAt / etaRange / primaryRoute / reasons`（例如 `disruption` 情景本身就是 `uncertain`，仍然给主路线 R2 与 Plan B R3）。
- 设计的「不确定」预览却把建议整块换掉，只留一张：
  > 资料状态｜目前资料存在较大波动｜部分实时资料延迟，建议预留至少 20 分钟缓冲时间｜重新获取建议
- 这是把**「决策不确定」（status=uncertain）**和**「资料延迟」**混为一谈，会让 D 误以为 `uncertain` 要清空结果。
- **改法**：区分两件事。
  1. `status = uncertain` → **照常显示完整建议**，只在顶部加一条黄色警示条（信心中/低 + 建议预留缓冲）。
  2. 「资料延迟/波动」→ 属于 `notices`（契约 additive 字段），应作为**叠加在结果之上的提示条**，不占用 `status` 的语义，名字也建议改为「资料更新中 / 资料延迟」。

### P0-6 「不可用」状态缺少契约要求的出口

- 契约 §2.4：`unavailable` → 使用者应「依 `reasons` 调整限制条件、改时间或改用其他方式」；`DecisionAction.hold` = 「留在安全处持续观察」。
- 设计只给了一个「重新获取建议」按钮，**没有**「修改条件重查」、没有 `hold` 行动、没有展示 `reasons` / `excludedRoutes`（为什么没路线可走）。
- 现有实作 `DecisionCard.tsx > UnavailableCard` 至少列出了 `reasons`，且保留「其他候选路线」入口；设计反而更弱。
- **改法**：不可用态至少给三个出口——① `修改行程条件`（主按钮）② `查看原因`（列出每条被排除路线与原因 = `excludedRoutes`）③ `留在安全处观察`（`hold`）。

## 四、建议改（P1）

### P1-7 「资料透明度」直接暴露英文技术词 `FIXTURE`

`labels.ts` 已规定中文（香港）标签为唯一来源：`live 實時資料 / cached 快取資料 / fixture 演示固定資料`。设计在结果页写「FIXTURE · 08:00」，页头又写「演示固定资料」——同一概念两种写法，且英文技术词更像开发者面板。
→ **改法**：统一用 `DATA_QUALITY_LABELS` 的中文标签；`FIXTURE` 只在 QA / 演示附录出现。

### P1-8 「额外车费」选项里没有 0、也没有演示基线 10

- 契约：`maxExtraCost` 为 0–500 的整数，**0 是有效值**且语义明确（只接受免费方案）；演示基线是 `maxExtraCost = 10`。
- 设计只有 `HK$40 / HK$80 / HK$150 以内` → 既选不出演示基线 10，也暗示「最少要花 40」，与契约口径冲突。
- **改法**：加「不额外付费（HK$0）」与「HK$10（演示基线）」，或改成 0–500 的输入框。
- （对照：转乘次数「不转乘 / 最多 1 次 / 最多 2 次」已覆盖 0，且都在 0–5 内，**OK**。）

### P1-9 「最迟到达时间」只有时刻、没有日期

- 契约 `arriveBy` 是 `YYYY-MM-DDTHH:mm`（香港时间），服务日期会影响结果；回应还带 `serviceDate`。
- 设计只显示 `09:00`。现有实作已回显「目标到达时间 / 服务日 / 前往地点」（`generatedFor`），设计应保留。
- **改法**：显示日期（或「今天 09:00」），并在结果页显示 `serviceDate`。

### P1-10 「推荐理由」是结论，不是可追溯的依据

- 契约硬规则：`reasons` 每条都要能追到 `basis`（`type: rule | data`），大模型不得生成事实。
- 设计的三条理由「波动更小 / 缓冲充足 / 可及时切换」没有任何来源标注，且第一条「**过去相似时段的行程时间较稳定**」与第二条小字「**基于相似行程表现**」**已构成统计依据（`type: statistics`）**——而 `DECISION_ENGINE.md` 明确：**没有历史校准前不得出现 `statistics` 依据，也不得声称统计或概率**。
- **改法**：① 每条理由后面挂来源（如「规则：缓冲 ≥ 8 分鐘」「资料：港铁服务正常（08:00）」）；② 删掉「过去相似时段」「基于相似行程表现」这类统计暗示，改为「演示估算」。

### P1-11 缺「其他候选路线 / 被排除路线」

- 契约 additive：`candidates`（依分数排序）与 `excludedRoutes`（排除原因）。`disruption` 情景的演示价值恰恰在于「R1 因服务中断被排除」，现有实作也有「其他候选路线」折叠块。
- 设计只给主路线 + 1 条 Plan B，用户无法回答「为什么不是另外那条」。
- **改法**：加可折叠的「其他候选路线（含被排除原因）」。

### P1-12 缺「查看原始 JSON / 决策依据」入口

现有实作在结果页提供「查看原始 JSON」按钮（README §6），便于向评委证明「结构化、确定性、可复现」。新版设计没有。
→ **改法**：保留该入口，或改为更友好的「查看决策依据」。

### P1-13 「行动建议」没有比较基准，且措辞与 `labels.ts` 漂移

- 设计出现：`按计划出发` / `提前出发` / `立即出发`。契约 `DECISION_ACTION_LABELS` 是 `立即出發 / 按建議時間出發 / 先核實再出發 / 留在安全處持續觀察`——设计把 `depart_at` 写成「按计划出发」，且缺 `wait` / `hold`。
- 且「提前出发」没有一个基准（相对习惯时间？相对建议时间？），用户读不出「提前多少」。
- **改法**：措辞与 `labels.ts` 对齐；在行动旁给基准，例如「比最迟出发早 10 分鐘」。

### P1-14 产品命名不统一

- 页头/页脚：「出行可靠性决策助手」；hero：「AI 出行可靠性决策助手」；Figma 文件名与项目名：「韧性出行助手」。
- 另外 hero 的「**AI** 出行可靠性决策助手」要小心：项目硬规则是「大模型不参与路线、时间、警告的事实判断」。宣传语可以讲 AI，但不能让评委理解成「路线是 AI 算的」。
- **改法**：统一命名（建议与项目名一致）；把「AI」的落点限定在「把结构化结果讲成人话」的副标题里。

### P1-15 「界面状态预览」是开发者控件，不应默认对用户可见

结果页底部有 4 个按钮（加载中/不确定/不可用/错误），这是给开发与 QA 用的状态切换器。对外演示或截图时会显得像半成品。
→ **改法**：放进「演示控制」折叠区、或只在 `?demo=1` 下显示、或用快捷键触发。

## 五、可选优化（P2）

16. **输入页缺「输入无效」的行内校验样式**（上一版 P0-2 已提，本次仍未画）：时间为空/格式错、车费非法值、未选地点。现有实作是红色卡片列出问题并聚焦首个错误字段，设计应对齐。
17. **「约 11.8 km」对地铁方案意义不大**，且与「港铁优先」标签混搭。建议改为「步行 7 分鐘 + 車程 30 分鐘」这种行动信息。
18. **风险等级用词不在契约内**：「低风险 / 中等风险 / 较高风险」需要由 C 定义映射或改用现有的 `RouteStatus`（服务正常/延误/中断/未确认）+ `riskNotes`。
19. **缺 `live` 情景**：契约 `Scenario` 有 4 个值（含 `live`），演示切换器只给 3 个。若刻意不给，建议在注释里写明原因（避免评审问「实时数据呢」）。
20. **无障碍再核一遍**：信心/风险已是「文字 + 图形」，方向正确；仍需确认正文对比度 ≥ 4.5:1、色盲友好、手机端主 CTA 落在拇指区。
21. `constraints` 在契约中标注为**必填**（✓），设计标注「**选填**」。若采用默认值请说明「预设 0／2」，避免与 `INVALID_INPUT`（为空即报错）矛盾。
