# UI 设计稿评审：页面结构稿 vs 项目构想

- 评审日期：2026-10-06
- 评审对象：`原始设计稿_页面结构.png`（页面 1 用户输入 / 页面 2 系统输出 / 场景页面）
- 对照基准：`韧性出行项目立项说明.docx`、`团队开发工作流.md`、已锁定契约 `resilience-travel-assistant/src/lib/types/decision.ts`、现有实现 `src/components/*`
- 评审身份：技术负责人视角（成员 A），关注"设计稿能不能直接交给 D 落地、会不会和契约打架"

---

## 一、总体结论

**方向对，但成熟度还停在"信息清单"，没到"决策工具"。**

这稿子抓住了正确的骨架：**输入 → 系统给出建议 → 情景切换**，和立项说明 §1、工作流 §3 的数据流完全一致；"行动建议（立刻出发/暂缓出发/提前出发）"这一层尤其好，它正是本项目区别于 Google Maps 的地方——用户要的不是更多信息，是"几点走、走哪条、什么时候换"。

但它缺了三样东西，而且这三样恰好都是项目验收里被点名要求的：

1. **数据可信度**：没有"数据更新时间 + 数据质量（live/cached/fixture）"。工作流 §7 完成定义明确要求"用户能看见数据时间戳和不确定性说明"，并且"不能把演示数据伪装成实时数据"。
2. **不确定 / 不可用状态**：页面 2 只画了"有结果"的样子，但契约里 `status` 有 `ready | uncertain | unavailable` 三态，还有加载中、输入无效、接口失败——团队规则是"不允许白屏"。
3. **可执行的切换条件**：稿子里只有"建议切换路线或者暂缓出发""切换路线原因"，缺"港铁延误超过 10 分钟改乘巴士""18:40 前必须离开"这种带阈值、带地点、带额外费用的硬条件。这是立项 §4 里写明的核心增量。

**粗略打分**：叙事与结构 8/10；与契约字段对齐 5/10；状态覆盖 3/10。

补完下面的 P0 四条，这份稿子就可以冻结成 v1 直接给 D 了。

## 二、符合项目构想的部分

| 设计稿元素 | 项目依据 | 判断 |
|---|---|---|
| 页面 1 输入页 / 页面 2 输出页两段式 | 工作流 §3 "用户填写行程 → 前端提交 TripRequest → 显示建议" | ✅ 完全一致 |
| 必填：起点、终点、到达时间 | 契约 `TripRequest` 的 `origin / destination / arriveBy` | ✅ 字段对得上 |
| 选填：出行偏好 | 契约 `constraints.maxExtraCost / maxTransfers` | ⚠️ 概念对，但口径太宽（见 P1-5） |
| 行动建议（立刻出发 / 暂缓出发 / 提前出发） | 立项 §5 "明确的暂缓或状态未确认提示"；代码 `DecisionAction` | ✅ 方向正确，甚至比工作流写得更贴近立项 |
| 推荐路线（路线 / 预计耗时 / 到达信心） | 契约 `primaryRoute` + `confidence` | ✅ 一致 |
| 风险预判（风险等级 / 原因 / 建议） | 工作流 §1 "推荐路线及其主要风险" | ✅ 一致 |
| 备用路线（路线 / 耗时 / 信心 / 切换原因） | 契约 `planB` + `planBPlan` | ✅ 一致 |
| 情景页面：正常通勤 / 极端天气 / 交通中断 | fixture `normal / heavy_rain / disruption` | ✅ 一一对应 |

结论：**没有跑偏，也没有超范围**（没出现登录、支付、全港搜索、精确准时概率）。问题全部集中在"信息够不够用、状态覆盖全不全、字段能不能对上"这三点。

## 三、必须改（P0，不改会在 10/11 验收和路演掉分）

### P0-1 补上"数据可信度"这一层

- 现状：页面 2 完全没有数据来源、更新时间、数据质量的位置。
- 问题：立项和工作流都把"不确定性说明"写成硬要求；演示数据不标注 = 把 fixture 伪装成实时数据，是团队规则 §6 明令禁止的。
- 改法：在页面 2 最顶部（一句话决策旁边）固定一个**数据新鲜度徽章**：`演示固定资料 · 2026-10-13 08:00` / `快取资料` / `实时资料`，三色区分但**同时带文字**。现有代码 `DataFreshnessBadge` + `DataSourceList` 已实现，设计稿照抄即可。

### P0-2 补上"不确定 / 不可用"状态页

- 现状：页面 2 只画了"系统输出了完整建议"的一种形态。
- 问题：契约有 `status = ready | uncertain | unavailable`，工作流要求"正常、加载、失败和无数据状态都可处理"，"不允许白屏"。
- 改法：页面 2 需要 5 个状态分支，设计稿要各给一版：
  1. **加载中**（骨架屏，明确"正在读取路线状态与天气资料"）
  2. **ready**（现稿的完整形态）
  3. **uncertain**（有建议但不确信，顶部黄条 + 提醒先核实官方信息）
  4. **unavailable**（无可执行建议 → 引导"暂缓出发 / 留观察 / 改条件重查"，**不是**一个空白或报错页）
  5. **接口失败**（可读错误 + 错误代码 + 重试按钮 + 返回输入页）
  另外输入页要有**输入无效**的行内校验样式（现在的实现是红色卡片列出问题）。

### P0-3 "切换条件"必须独立成块，并且是硬阈值

- 现状：切换条件散在"风险预判"和"备用路线 → 切换路线原因"里，只有"建议切换"的定性表述。
- 问题：用户要能回答"几点前必须走、什么信号一出现就换线"。这是立项 §4 明确写下的项目增量，也是演示脚本第 3 步的主打台词。
- 改法：结果页单独开一个高优先级区块：

  > **切换条件**：08:20 前必须离开坑口站；若港铁将军澳线延误超过 10 分钟，改乘过海巴士（额外 $12）。

  必须包含三要素：**阈值时间或事件** + **切换地点** + **额外费用/代价**。现稿的"切换路线原因"只是解释，不是条件。

### P0-4 到达时间写"区间"，信心加限定词

- 现状："预计到达时间"是一个点，"到达信心"没有口径说明。
- 问题：契约是 `etaRange: [最早, 最迟]`；工作流 §1 特别注明"在没有足够历史数据校准前，界面使用'到达信心 高/中/低'或'演示估算'，**不要声称拥有准确准时概率**"。
- 改法：显示为 `09:02 – 09:14`；信心标签写成 `到达信心 高（演示估算）`，禁用"准确率 92%"这类表述。

## 四、建议改（P1，影响可用性和团队协作）

### P1-5 输入口径三处要收紧

| 稿子写的 | 问题 | 建议 |
|---|---|---|
| "期望到达时间" | 语义模糊：是"最迟"还是"希望"？决定引擎算不出该"提前"还是"暂缓" | 改为**"最迟到达时间（香港时间）"**，对应 `arriveBy` |
| "起点、终点"（看着像自由输入） | 首版明确不做全港任意路线搜索 | 改为**走廊预设单选**（如：坑口（富宁花园）/ 坑口站 A 出口；中環（交易广场）/ 中環 IFC） |
| "出行偏好"（自由选填） | 范围蔓延的口子，AI 生成代码时最容易在这加功能 | 收敛为契约里的**两条硬约束**：可接受额外车费（HKD）、可接受转乘次数。明确"0"是有效值（0 车费 = 只走免费方案） |

### P1-6 写清"情景切换"的两种语义

- 现状："场景页面（不同状况下进行切换）"容易被读成"用户自己选今天什么天气"。
- 真实产品：情景应由数据判定（天气警告、交通公告），**用户不选**。
- 演示阶段：情景切换器是 demo affordance，必须标"演示情景 · 固定资料"，并说明切换会写进 URL 所以刷新结果一致。
- 改法：设计稿加一行注释区分这两者，避免路演被评委问"用户怎么会自己选暴雨"。

### P1-7 页面 2 补"推荐理由"

契约有 `reasons: string[]`，立项 §5 要求"主要不确定性及所需时间余量"。现稿有"到达信心"但没交代**为什么**是信心高/低。建议加一条可折叠的"推荐理由"，每条理由必须能追到规则或数据（工作流 §6：大模型只能解释，不能生成事实）。

### P1-8 信息层级：页面 2 第一屏要能"5 秒读完"

- 现状：建议出发时间、到达时间、行动建议、推荐路线、风险、备用路线、切换条件平铺 7~8 条。
- 问题：用户测试要检验的是"用户能不能不假思索地找到：几点走、走哪条、什么时候换"。平铺会让主角信息被淹没。
- 改法：分三层
  1. **一句话决策**（最大字号）：`08:10 出发 · 09:02–09:14 到达 · 建议立即出发`
  2. **为什么可信**（次级）：到达信心 + 数据新鲜度徽章 + 服务状态
  3. **细节**（可展开/下滑）：主路线时间轴、Plan B、切换条件、风险、理由、候选路线

## 五、可选优化（P2）

9. **行动建议要有判定基准**：稿子写"立刻出发/暂缓出发/提前出发"，但没写相对谁。建议明确为"相对建议出发时间 / 最迟出发时间"，并补上第 4 种动作 **"留在安全处持续观察"**（对应 `DecisionAction.hold`）。现实现已支持 4 种动作。
10. **三情景共用一个骨架**：稿子已经写成"核心决策信息 + 情景差异"，方向对，建议在设计稿里直接标成"**一个结果页骨架 + 天气/中断说明插槽**"，否则 D 容易做成三套页面。
11. **不要只靠红黄绿表达风险/信心**：加图标 + 文字（色盲友好），正文对比度至少 4.5:1；手机端保持单列，主 CTA 放拇指区。
12. **底部固定演示声明**：`演示原型 · 时间为估算值，非官方班次`，防止演示被当作真实产品承诺。

## 六、建议的改版页面结构（可直接给 D 落地）

### 页面 1 · 行程输入

```
你的行程（首版只支援一條固定通勤走廊）

起点（单选）   ○ 坑口（富寧花園）   ○ 坑口站 A 出口
终点（单选）   ○ 中環（交易廣場）   ○ 中環（國際金融中心二期）
最迟到达时间   [ datetime-local ]   ← 必填
—— 高级限制（可折叠）——
可接受的额外车费（HKD）  [ 10 ]
可接受的转乘次数        [ 2 ]
演示情景（标注：固定资料） [正常通勤][暴雨影响][交通中断]

[ 取得出行建议 ]      ← 主 CTA
* 输入无效时：行内红色提示，不跳页
```

### 页面 2 · 出行建议（一个骨架，5 个状态）

```
┌ 状态：loading / ready / uncertain / unavailable / error ─┐

[一句话决策]  08:10 出發 · 09:02–09:14 到達 · 建議立即出發
[到達信心 高（演示估算）]  [演示固定資料 · 08:00]  [服務正常]

── 主路線：將軍澳線 → 港島線（時間軸 + 每段步行/候車）──
   全程 52 分鐘 · 轉乘 1 次 · 額外車費 $0

── Plan B：過海巴士 692（+$12，+9 分鐘）──
── 切換條件（高亮）：08:20 前必須離開；延誤 > 10 分鐘改乘巴士 ──
── 風險預判：中 · 主要風險原因 · 建議動作 ──
── 推薦理由（可折叠，每條可追溯到規則/資料）──
── 資料來源與時間（live / cached / fixture + 時間戳）──
── 其他候選路線（可折叠）──
── 免責：到達信心為定性判斷，非校準過的準時機率 ──

unavailable 时顶部替换为：目前沒有可執行的建議 → 暫緩出發 / 留在安全處觀察 / 修改條件重查
```

## 七、与已实现契约的字段对照（避免设计稿和代码两套字段）

| 设计稿元素 | 契约字段 | 现有实现位置 | 缺口 |
|---|---|---|---|
| （缺） | `status: ready/uncertain/unavailable` | `DecisionCard` 三态 | 设计稿未画 uncertain/unavailable |
| 建议出发时间 | `departAt` / `latestDepartAt` | `PrimaryRecommendation` | 稿子缺"最迟出发" |
| 预计到达时间（点） | `etaRange: [起, 止]` | ✅ 已显示区间 | 稿子要改区间 |
| 到达信心 | `confidence` | ✅ | 稿子要加"演示估算"限定 |
| 行动建议 | `action: depart_now/depart_at/wait/hold` | `DECISION_ACTION_LABELS` | 稿子缺 `hold` |
| 推荐路线 | `primaryRoute` / `primaryPlan` | `RouteTimeline` | ✅ |
| 风险预判 | `primaryPlan.riskNotes` / `RouteStatus` | ✅ | ✅ |
| 备用路线 | `planB` / `planBPlan` | ✅ | ✅ |
| 切换原因（定性） | `switchCondition`（应为硬条件） | ✅ | 稿子要升级为阈值 |
| （缺）推荐理由 | `reasons` / `basis` | ✅ | 设计稿未画 |
| （缺）数据时间与质量 | `dataUpdatedAt` / `dataQuality` / `dataSources` | `DataFreshnessBadge` | 设计稿未画 |
| （缺）提醒与免责 | `notices` / `disclaimer` | `NoticeList` | 设计稿未画 |

> 提醒：`src/lib/types/decision.ts` 标注为"契约所有者：成员 A"，**字段名和类型不得由 E/D 独自改动**。设计稿需要新字段时，先回到契约讨论，再加到 additive 区。
