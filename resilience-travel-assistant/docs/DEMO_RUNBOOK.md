# 演示執行手冊（DEMO RUNBOOK）

> 目標：**任何情況都能把演示跑完。**
> 負責人：成員 A。演示前 30 分鐘由 A 逐項打勾。

---

## 0. 三重備份

| 順位 | 形式 | 準備方式 | 使用時機 |
|---|---|---|---|
| 1 | 線上／本機版 | `npm run build && npm run start` | 正常情況 |
| 2 | 離線 fixture 版 | 同上，本機執行（**不需要網路**） | 現場 Wi-Fi 不穩 |
| 3 | 演示錄屏 | 事前用手機錄一次完整流程 | 電腦／瀏覽器故障 |

**本應用的 API 與頁面同源**，所以「離線版」就是本機 `npm run start`。
只要 Node 還在跑、瀏覽器還能連 `localhost`，就算完全斷網也能完成演示。

## 2. 正常演示（約 3 分鐘）

### 步驟 1：輸入行程（30 秒，操作人）

1. 打開首頁。
2. 起點選 **坑口（富寧花園）**。
3. 終點選 **中環（交易廣場）**。
4. 最遲到達時間保持 **2026-10-13 09:00**。
5. 額外車費上限 **10**、轉乘上限 **2**。
6. 情景選 **正常通勤** → 按「取得出行建議」。

### 步驟 2：說明結果（60 秒，主講）

指著四個地方，依序說：

1. **建議出發時間 08:09** —— 「不是顯示幾條路線，而是直接告訴你幾點要走。」
2. **到達範圍 08:54–09:04、到達信心 高** —— 「而且告訴你這個建議有多可靠。」
3. **主路線** —— 「港鐵主線 45 分鐘；因為它最快，而且服務正常。」
4. **切換條件** —— 「如果將軍澳線延誤超過 10 分鐘，就改到坑口（北）搭過海巴士。」

### 步驟 3：切換情景（60 秒，操作人）

在結果頁上方的情景切換器依序按 **暴雨影響** → **交通中斷**，每次說一句：

| 情景 | 畫面變化 | 說明 |
|---|---|---|
| 正常通勤 | 08:09 出發，信心 **高**，主路線 **R1** | 基準 |
| 暴雨影響 | 07:58 出發（**早了 11 分鐘**），信心 **中**，主路線仍 R1，緩衝由 6 分鐘變 14 分鐘 | 系統自動把不確定性換成時間緩衝 |
| 交通中斷 | 07:22 出發，信心 **低**，主路線換成 **R2 過海巴士**，R1 被列為「服務中斷」 | 主路線真的改變，不只是換文案 |

### 步驟 4：收尾（30 秒，主講）

1. 捲到「**資料來源與時間**」區塊。
2. 說明：「畫面上這一行寫著**演示固定資料**與資料時間 —— 我們不會把演示資料偽裝成實時資料。
   接上真實 API 後這裡會變成『實時資料』，程式碼不需要改。」
3. 說明核心差異：「我們不是多給你幾條路線，而是把天氣和交通轉成
   **幾點走、走哪條、什麼時候切換**。」

## 3. 斷網演示

### 情況 A：本機執行、完全沒有網路

**不需要做任何事。** 直接照 §2 演示即可。

- 頁面與 API 都來自 `localhost`。
- 三個情景都是本機 fixture，不連外網。
- `live` 情景會顯示回退訊息（見 §4）。

### 情況 B：使用線上版但網路中斷

1. 立即切換到本機的 `npm run start`，用同一個網址流程繼續。
2. 若來不及切換，改播錄屏備份，並口頭說明架構與降級設計。

### 情況 C：想主動示範「實時資料失敗會怎樣」

在 `localhost:3000/result?...&scenario=live` 打開 `live` 情景。
因為沒有設定實時來源，畫面會：

- 正常顯示建議（回退到 fixture）；
- 在「提醒」區塊顯示「未設定實時資料來源…本次使用演示固定資料」；
- 資料品質標籤是灰色的「演示固定資料」。

這句話就是最好的降級演示：**失敗不會白屏，而是誠實降級。**

## 4. 故障恢復

| 症狀 | 原因 | 復原動作 |
|---|---|---|
| 畫面顯示紅色「無法取得建議」 | API 500 或網路失敗 | 按「**重試**」；無效則重新整理（`Cmd/Ctrl + R`） |
| 一直顯示載入中 | 上一次 `delay` 故障注入未結束，或 server 掛掉 | 等 3 秒；無效則重啟 `npm run start` |
| 顯示「目前沒有可執行的建議」 | 到達時間太早或限制條件太嚴 | 這是**預期行為**；改回 09:00 / 上限 10 繼續演示，或當作功能示範 |
| 白屏 | 前端崩潰 | 應不會發生（有 `error.tsx`）；真的發生就重新整理，仍失敗則用錄屏 |
| 頁面 404 | 網址被改壞 | 回首頁重做一次輸入 |
| server 無回應 | 進程被關 | `npm run start`（必要時先 `npm run build`） |

### 一鍵重置

```bash
# 停止伺服器：Ctrl + C
npm run build && npm run start
# 瀏覽器回到 http://localhost:3000
```

沒有任何需要清理的狀態：沒有資料庫、快取在記憶體（重啟即清空）、
結果完全由 URL 決定。**「重置」就是重新整理瀏覽器。**

## 6. 答辯可能的問題

| 問題 | 回答要點 |
|---|---|
| 這和 Google Maps / Citymapper 有什麼不同？ | 它們給路線與 ETA；我們在**你的到達時限與限制條件下**直接給出「幾點走、走哪條、什麼時候切換」，並在出發前就備好 Plan B。 |
| 到達信心怎麼算？憑什麼？ | 是**規則分數的定性分級**（服務狀態、延誤、人流、轉乘、緩衝、資料品質），**不是準時機率**。校準需要歷史資料，是賽後工作。 |
| 資料是真的嗎？ | 不是。畫面明確標示 `fixture` 與固定資料時間。畫面上不會出現任何未標示的假實時資料。 |
| 為什麼建議巴士比港鐵快時還是選港鐵？ | 不會。評分裡時間佔 0.40，服務狀態佔 0.25；中斷情景下主路線真的會換成巴士。 |
| 大模型在哪裡？ | 只用在把已算好的結果解釋成人話，**不參與路線、時間與切換條件的事實判斷**。 |
| 真實 API 失敗怎麼辦？ | 三層回退：live → cached → fixture。任何一層失敗都會顯示提醒而不是白屏。 |
| 為什麼只有一條走廊？ | 刻意的範圍限制。先把一條走廊的資料與決策做對，擴展方式是新增路線定義而不是改架構。 |
| 如果要做全港？ | 需要 `corridor/` 的多走廊資料與真實資料源；分層架構不需要改。 |
