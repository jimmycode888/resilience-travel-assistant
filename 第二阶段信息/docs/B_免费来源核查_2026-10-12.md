# B 部分「先用公开免费来源」可行性核查（2026-10-12）

核查人：B 部分（数据源与实时信息适配层）｜方式：对官方端点做一次真实联网探测，结果存档在
`docs/data/free-source-probe-2026-10-12.json`（含 HTTP 码、耗时、字节数、响应样例）。

---

## 一、结论

**能，而且可行度很高，但要用对口径。**

B 目前已经接入的来源**全部**是公开、免费、无需注册、无需密钥的政府开放数据（HKO、MTR Next Train、城巴 ETA、运输署特别交通消息、港铁静态站序/票价）。
也就是说「先用公开免费来源」不是备选方案，**它本来就是 B 的主路径**，本次核查只是把「还能不能继续免费做下去」这件事用实测证据钉死。

真正的问题不是「要不要花钱」，而是**官方根本不公开**：口岸实时排队时间、港铁延误分钟数、深圳侧实时交通。
所以正确策略是三段式：

1. **免费公开源先用满**（本节三、五节的 A 档，零配置、零密钥，断网仍可走 fixture）；
2. **拿不到的如实降级**为「历史规律 + 时段模型」→ 区间 + confidence，明确标注估算，绝不编造；
3. 只有在「必须做真实全程 ETA / 深圳侧路径」时才考虑 B 档（需注册的免费额度地图 API），且默认关闭、只放 `.env.local`。

## 三、本次核查发现的 3 个「免费可得、但还没用上」的提升点

### 1. 九巴 KMB ETA API —— 补上现在「只涵盖城巴」的联营缺口（P1，收益最大）

- 现状：`src/lib/adapters/transport-times.ts` 的 `BUS_TIME_POINT` 只有 `CTB/690S/002910/I`，note 里写着「只涵蓋城巴班次；九巴時段…不可推論停駛」。
- 实测：`data.etabus.gov.hk` 九巴 ETA 系列**完全免费、无需 key、无需注册**。
- ⚠️ 关键细节：九巴用**自有 stop id**（如 `5016E25156D72ADA`），**不能**把城巴的 `002910` 直接套进去，必须先用 `route-stop/{route}/{bound}/{service_type}` 做站点映射，再用 `eta/{stop}/{route}/{service_type}` 取到站。
- 收益：690S／690 是城巴＋九巴**联营**，接上之后「空 ETA」的解读才站得住——两公司都空才是真的没有班次，而不是「同一班车只是不归城巴开」。

### 2. 东铁线过境段可直接 live，B6 跨境不必走 fixture（P0，免费）

- 实测 `EAL-LMC`（落马洲）、`EAL-LOW`（罗湖）、`EAL-SHS`（上水）全部 200，和现有 3 个港铁时间点**同一套 client**即可。
- ⚠️ 方向过滤不能照抄：坑口用 `dest=NOP`，而落马洲/罗湖返回的是 `dest=ADM`（往金钟方向），必须按**真实响应里的 dest/plat** 过滤，不能硬编码。
- 收益：B6「东铁线过境段服务状态」从「只能靠口岸基础数据 + fixture」升级为有真实 live 观测，跨境是本次第二阶段最高优先级，这一条性价比最高。

### 3. HKO 预报类端点免费可用（fnd / swt）

- `fnd`（9 天预报）200、`swt`（特别天气提示）200。
- ⚠️ 只能用于「未来时段」查询，且必须与 `snapshot.serviceDate` 对齐；不能拿现在的实时观测当未来事实（这是 B 现有协作审查里已列明的红线）。
- `warnsum` 已提供 `name / code / issueTime / expireTime`；`warninfo` 需要额外参数，实测直接请求会返回参数提示页，**不要**据此编造 `preAnnounceAt`。

## 四、免费也拿不到的（硬约束：如实标注，不编造）

| 缺口 | 核查结论 | 处理方式 |
|---|---|---|
| **口岸实时排队时间**（香港侧 + 深圳侧） | 两边都**没有公开 API**；data.gov.hk 目录检索 0 命中 | 降级为「历史规律 + 时段模型」→ **区间 + confidence(low/medium)**，UI/文档明确写「估算」 |
| **港铁延误分钟数** | Next Train 只有 `isdelay=Y/N`，**无分钟值**；也没有官方线路服务状态 API | 只用 `alert` / 公告 + 如实标注；「alert ≠ 全线停驶」 |
| **深圳侧实时路况 / 地铁到站** | 无免 key 官方 API（深圳市政府数据开放平台需实名注册） | fixture + 标注；能用地图 API 时再作为可选增强 |
| **全程行车时间 / 候车班距** | 官方无公开的逐 OD 行程时间 API；Next Train 是「当前站抵站」不是全程旅时 | 现状 fixture 是**正确**的；若要真实值只能走 B 档地图 API |

## 五、来源分级建议

**A 档 —— 无 key、无登录、公开开放数据，直接可用（B 的主力）**
HKO 天气/警告/预报 · MTR Next Train（含东铁过境站 LMC/LOW/SHS）· 九巴 KMB ETA · 城巴 ETA · 运输署特别交通消息 · 港铁静态站序/票价 CSV。

**B 档 —— 免费但要注册 key，非必须，仅在「要做真实全程 ETA / 深圳侧路径」时启用**
高德 / 百度 / 腾讯地图路径规划与出行时间。密钥只进 `.env.local`，`.env.example` 只写变量名与含义；默认关闭，演示不依赖。

**C 档 —— 无任何公开来源，必须降级并标注**
口岸实时排队 · 港铁延误分钟 · 深圳侧实时交通。

> 结论：**A 档已经能覆盖跨境主链路的「能不能走、走的哪一段、口岸开不开、铁路通不通」，够支撑演示与验收。B 档不建议现在引入**，因为它会引入密钥管理成本，却换不来决定性的新事实（排队时间它也给不出权威值）。

## 六、建议落地顺序（全部免费源，可逆、可测、不破坏现有 172 项基线）

1. **P0 · 东铁过境站接入**：把 `LMC/LOW/SHS` 加进 `MTR_TIME_POINTS`（注意 dest=ADM 的方向过滤），补单测（方向、空响应、超时三用例）。跨境节点从此有真实 live。
2. **P0 · 数据源核对表新增「跨境」独立一节**：口岸清单 / 开放时间 / 可通行方式写成「官方页面核查 + 存档」，排队时间明确标注「估算区间 + confidence」。
3. **P1 · 九巴 ETA 接入**：先做 route → stop 映射，再与城巴合并为「联营覆盖」，note 改为「两公司时段的空值皆不可推论停驶」。
4. **P2 ·（可选）地图 API**：仅用于深圳侧与全程时间，opt-in、默认关闭。

---

## 七、与现有硬约束的一致性

- A 档来源全部走 `live → cached → fixture` 三退路链，`dataQuality` 三态如实填写，**断网仍以 fixture 完整演示**。
- **零密钥**：A 档无需任何密钥，演示环境零配置即可跑；B 档若引入，密钥只放 `.env.local`。
- 抓取字段（`line/sta/dest/plat`、九巴 stop id、口岸代码）**按真实响应核对**，不硬编码 AI 猜测的字段名。
- 估算类数据（口岸排队）一律带区间 + confidence，**不出现精确到分钟的假实时**。
